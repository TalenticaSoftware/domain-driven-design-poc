Why DDD exists

The translation gap is where bugs live

❌ Without DDD — two languages
"Place an order"INSERT INTO purchase_records
"Approve invoice"SET status = 2
"Customer cancelled"is_active = false
✅ With DDD — one language
"Place an order"order.place()
"Approve invoice"invoice.approve(mgr)
"Customer cancelled"subscription.cancel(reason)

DDD eliminates this translation gap. Business language and code language become the same language.

Pillar 1 — Core Philosophy

Ubiquitous Language

Domain Expert

"When an order is placed, we check inventory and schedule delivery."

same words

Developer

order.place() → OrderPlaced → scheduleShipment()

  • One term, one precise meaning — inside each Bounded Context
  • The code IS the documentation — rename in glossary → rename in code
  • No technical jargon in the model: no "Handler", "Manager", "Processor"
  • A domain expert should be able to read class names and understand them

Architecture

Hexagonal — Ports & Adapters

1

Domain at the centre

Pure TypeScript — no TypeORM, no Express, no framework at all. Just business logic.

2

Ports — interfaces in domain

IOrderRepository, IEventBus — defined by domain, implemented outside.

3

Adapters — infrastructure

TypeOrmOrderRepository implements the port. Swap DB without touching domain.

4

One rule: arrows point inward

Infrastructure knows domain. Domain knows nothing outside itself.
